## Render Inference

Render is the likely next hosting target because the coworker-facing v1 probably
needs server-side state that GitHub Pages cannot provide:

- login or role boundaries;
- human classification writes;
- review and publication state;
- scheduled or manually triggered ingestion;
- server-side secrets for future providers;
- a database that can survive deploys and be backed up.

This is an inference, not yet an implemented architecture. The repo does not yet
contain the Render app.

## Minimum Render Shape To Decide

Before implementation, Atlas and the Claude orchestrator should ask Otavio to
choose or approve these points:

- Web app framework: Flask, FastAPI, Django, or another stack.
- Database: SQLite on a Render persistent disk for a small v1, managed Postgres,
  or a separate hosted database.
- Worker model: web-only manual ingestion, Render cron job, background worker,
  or external scheduler.
- Auth model: shared password, per-user login, Google login, or another gate.
- Classification scope: article-level, story-level, or both.
- GitHub Pages relationship: keep as legacy/static snapshot, replace it, or
  publish from Render while preserving Pages for public read-only views.

## Secret-Safe Render Rules

- Store secrets only in Render environment variables or another server-side
  secret store.
- Never paste provider keys, deploy hooks, database URLs, cookie secrets, or key
  previews into chat, Markdown docs, frontend code, backend logs, screenshots,
  or exported reports.
- Render logs should contain safe metadata only: job names, counts, timings,
  status codes, and sanitized error categories.
- Any AI-summary generation in the future needs an admin gate, budget rule,
  audit trail, and provider-key policy before regular coworkers can use it.

## First Render Implementation Task

The first code task should not be "deploy the existing `server.py`". That file
generates static snapshots and is not a service process.

A safe first implementation task is:

1. Add a small web app entrypoint that reads from the clipping database and
   exposes a read-only review page or API.
2. Add a Render start command that binds to `PORT`.
3. Add a deployment config or documented Render dashboard settings.
4. Add secret-safe environment variable names without values.
5. Add a smoke test that verifies the app can start locally.

Only after that should the project add classification writes, authentication,
scheduled ingestion, or AI-provider integration.

## Git Sync Protocol While Claude Code Is Active

Because Claude Code may be changing the cloud copy at the same time:

1. Run `git status --short --branch` before editing.
2. Run `git fetch origin` before any push.
3. If `master` is behind or diverged, inspect the remote commit before pushing.
4. Prefer a normal merge for shared history unless there is a clear reason to
   rewrite local unpushed commits.
5. If rewriting a local commit is necessary, first create a backup branch.
6. Commit meaningful changes in small checkpoints.
7. Push after each checkpoint that Claude Code needs to see.
8. Do not push virtualenvs, cache directories, temporary probe databases, or
   generated logs unless Otavio explicitly asks for those artifacts.
